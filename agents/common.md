# 通用协作规范（语言无关）

供各项目 AGENTS.md 引用的**语言无关**通用规范。项目侧文件通过相对链接引用本文件后，以下条目对AI 助手 / 自动化任务的每一次循环生效；项目绑定规范（如 spec 位置、仓库结构）以项目侧文件为准，两者冲突时**项目侧优先**。

## 1. 规格与进度文档

- 项目应维护规格文档（需求边界、API 契约、验收场景）与任务清单。
- **所有任务开始前必须先读规格文档**并遵循其规定。实现与规格冲突时：
  1. 若规格本身有误或需求变化，先修改规格（并在任务清单记录修正缘由），再改代码；
  2. 严禁绕过规格直接实现（例如为让测试通过而"避开"某些用例组合——此类做法已被证明会掩盖真实缺陷）。
- 规格中标注「设计决策，勿重复讨论」的需求为已定论，除非出现明确新需求，不重启讨论；推翻属 BREAKING，须在规格显式声明并说明迁移方式。
- 每完成一项任务，在任务清单勾选或追加对应条目；行为变化同步更新规格与验收清单。

## 2. Git 提交规范（强制）

- **每次被接受的修改（用户确认或任务验收通过）都必须做一次 git commit**，不积攒多个任务的改动。
- 提交信息使用**中文 Conventional Commits** 格式：

  ```
  <类型>: <中文摘要，50 字符内，不加句号>

  <正文：动机与要点，中文，每行 ≤ 72 字符，可省略>
  ```

- 类型取值：`feat`（新功能）、`fix`（缺陷修复）、`refactor`（重构）、`test`（测试）、`docs`（文档）、`perf`（性能）、`chore`（构建/工具）。
- 提交前必须确认 `git status` 干净合理、`git diff` 只含本次任务的改动；**不提交**密钥、临时产物与环境 dotfile（如 `.env.*`，以各项目 `.gitignore` 为准）。
- 禁止 `--force` 推送、禁止改写历史；仅在被明确要求时推送远端。
- 多行提交信息：POSIX shell（WSL）下直接用 heredoc：`git commit -m "$(cat <<'EOF' ... EOF)"`。

## 3. 路径与环境的文档中立性（强制）

- 凡**进入 git 提交的任何文档**（AGENTS.md 及其引用的规范文件、规格文档、README、代码注释、commit message 等）：
  - **禁止**出现本地绝对路径（盘符路径、`/home/...`、`/mnt/...`、`C:\Users\...` 等）与用户名、机器名等环境特定信息；
  - **只允许**使用相对项目根目录的路径（如 `spec/spec.md`、`build.go`）；仓库根目录一律表述为「项目根目录」或 `.`。
- 本地绝对路径**唯一合法的存放处**是 `.env.*`（不提交）。

## 4. 注释与文档语言

- 代码注释、提交信息、规格与验收文档一律使用**中文**；标识符用英文。

## 5. 工作循环（每次任务必须遵守）

1. **读环境**：读根目录当前环境对应的 `.env.*` 文件（存在则直接采用探测结论；缺失才重新探测并回写）。
2. **读规格**：从规格文档起手，明确需求边界与验收场景。
3. **查进度**：读任务清单（含实现期修正记录，勿重蹈覆辙）。
4. **最小实现**：只做被要求或显然必要的改动；不过度设计、不提前抽象。
5. **自验证**：跑本语言静态检查与测试门槛全部命令；对照验收清单。
6. **更新文档**：勾选/追加任务清单与验收清单；行为变化同步更新规格。
7. **提交**：按第 2 节规范 git commit。

## 6. Shell 环境规范（WSL）

- 开发环境为 **Remote-WSL**（Ubuntu，POSIX 登录 shell）：工具链均在 PATH 中，直接以命令名执行。shell 命令与提交信息一律按 POSIX 语义执行。
- 环境探测结论持久化于根目录 `.env.<环境名>`（如 `.env.win` / `.env.wsl`）：每次任务开始先读当前环境对应文件并直接采用；环境变化只更新对应环境的文件，互不覆盖；新环境按同一命名规则新增。
- 记录内容：OS / 发行版、工具链路径与版本、项目路径、验证结论（含 -race 等本环境无法运行的项的替代执行方式）。
